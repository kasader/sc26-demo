## 2. なぜカーネルの中でやるのか（1:10）

[victim ペインを指し、そのあとパケットの経路を描く、または指す。]

> あのサーバーにゴミパケットを大量に送りつけたとき、実際にネックになるのは、
> 普通は帯域ではありません。たいていの人は「帯域」と答えますが、
> そこじゃないんです。ここです。

```text
NIC → ドライバ → [sk_buff を確保] → iptables → IP → UDP → ソケット → アプリ
```

[確保のところを指す。ここが今日の話の核心なので、ここだけは急がない。]

> パケットが1個届くたびに、カーネルはそれを管理するための小さな構造体 —
> sk_buff — をメモリに確保します。そのあとファイアウォール、IP層、UDP層を
> 通って、最後にアプリケーションに渡される。
> そしてアプリが中身を見て「これはゴミだな」と言って捨てる。
>
> **この「確保」が問題の全部です。**
> 捨てると最初から決まっていたパケット1個のために、確保して、解析して、
> ルーティングして、コピーして、プロセスを起こしている。
> これを毎秒10万回やられたら、マシンは倒れます。
> 回線が埋まったからではありません。
> **迷惑メールの事務処理にCPUを全部使い切ったから**です。
>
> なので直し方は明らかです。もっと早い段階で捨てればいい。
> 問題は、どこまで早くできるか、です。

[経路の一番手前、確保より前を指す。]

> その答えが XDP です。カーネルがまだ何も確保していない段階で動くフックです。
> パケットは回線から届いたばかりで、メモリ上のただのバイト列でしかない。
> 私のコードはそのバイト列を見て、二つのうちどちらかを答えます。
> PASS — 通常のネットワークスタックにそのまま流す。
> あるいは DROP — この場で解放する。
> ここでの DROP はほぼコストゼロで、しかも送信元には何も返りません。
> エラーすら返らない。
>
> ただ、これはカーネルの中で動くコードです。
> 昔はカーネルモジュールを書くしかなくて、書き間違えたらマシンごとパニックでした。
> そこで eBPF を使います。C言語で書いて、専用のバイトコードにコンパイルして —
> 普通の実行ファイルではありません — そのバイトコードを、
> 動いているカーネルに渡します。再起動なし、モジュールなし。
>
> そして「クラッシュしない」理由が、この技術の一番面白いところです。
> カーネルは、私の命令を1個も実行する前に、verifier（検証器）を走らせます。
> verifier は証明エンジンで、2つのことを証明しないといけない。
> **必ず終わること**、そして
> **許可された範囲の外のメモリを絶対に読まないこと**。
> 証明できなければ、プログラムはロードされません。
> あとで落ちるのではなく、そもそも受け付けてもらえない。
>
> なので、このあと一見不要に見える境界チェックがいくつも出てきますが、
> あれは「念のため」ではありません。
> **あれが証明で、カーネルが採点している**んです。

## 3. レイヤ1: レート制限（1:50）

[guard ペイン。先にダッシュボードを Ctrl+C。
これは git を読むだけなので失敗しないし、まだ何も変わらない。]

```bash
./stage.sh show 1-2
```

> これが1層目です。コードは30行くらいで、あとは全部コメント。
> 中身は2つの考え方でできています。

**その1 — こいつは誰か、そしてもう出禁にしていないか:**

```c
  struct address_key src = {
      .address = bpf_ntohl(iph->saddr),
      .port = bpf_ntohs(udph->source),
  };

  if (bpf_map_lookup_elem(&blocklist, &src)) {
    inc_stat(2);
    return XDP_DROP;
  }
```

> まず送信元の「身元」を作ります。IPアドレスと、ポート。
>
> **IPと、ポート。これ、覚えておいてください。**
>
> そしてハッシュを1回引くだけ。
> この送信元がすでにブロックリストに載っていたら、その場で終わり。
> それ以上1サイクルも使いません。
> これは最適化ではなく設計の原則です。
> **すでに悪いと分かっている相手のチェックが一番安いので、それを最初に置く。**

**その2 — どれくらいの速さで送ってきているか:**

```c
  __u64 now = bpf_ktime_get_ns();
  struct rate_state *rs = bpf_map_lookup_elem(&rate_track, &src);
  if (!rs) {
    struct rate_state init = {.window_start_ns = now, .count = 1};
    bpf_map_update_elem(&rate_track, &src, &init, BPF_ANY);
  } else if (now - rs->window_start_ns > RATE_WINDOW_NS) {
    rs->window_start_ns = now;
    rs->count = 1;
  } else {
    rs->count++;
```

> 送信元ごとに1秒のウィンドウを持ちます。
> 最初のパケットでウィンドウを開始。1秒経っていたらリセット。
> それ以外はカウントを増やす。

**その3 — で、線を越えていたら:**

```c
    if (rs->count > rate_threshold) {
      struct block_event evt = {.address = src.address, .port = src.port,
                                .count = rs->count};
      bpf_ringbuf_output(&block_events, &evt, sizeof(evt), 0);
      inc_stat(2);
      return XDP_DROP;
    }
```

> しきい値 — 毎秒30パケット — を超えたら、この送信元はフラッディングしていると
> 判断します。ここで2つのことが起きます。
> ユーザー空間のGoプログラムにメッセージを送って、
> この送信元を15秒間ブロックリストに入れてもらう。
> そして**そのパケット自体は、いま、この場で、カーネルの中で落とす**。
>
> Goプログラムを待ちません。Go側がそのメッセージを読む頃には、
> ドロップはとっくに終わっています。
> **カーネルが執行し、ユーザー空間は記録をつけているだけ**です。

### 実際に動かして flood を実行

[ステージ2をチェックアウトし、ビルドし直し、guard を再起動する。
数秒かかって、途中の手順が表示される。黙って待たずに喋りながらやる。]

```bash

```

> 表示される3行を見ていてください。これがパイプライン全体です。
> Cを取って、バイトコードにコンパイルして、動いているカーネルに渡す。
> そこで verifier が、パケットに触る前にチェックします。

[攻撃側のペインで:]

```bash

```

> 攻撃者2つ、それぞれ毎秒150パケット。制限の5倍です。

[dropped-rate が伸びるのを指し、次にブロックリストのパネルを指す。]

> ブロックリストに載りました。15秒のカウントダウン付きです。
> で、これが切れるとどうなるか、見ていてください。

[のこぎり波（sawtooth）が出るまで待つ。]

> ブロックが外れて、攻撃者が再開して、0.2秒くらいでまた制限を超えて、
> すぐ載り直す。
> このギザギザが、TTLがちゃんと働いている証拠です。
>
> さて。レート制限、効いていますね。これで一件落着でしょうか?

## 5. レイヤ2: 「どれくらい」ではなく「何を」を聞く（1:20）

> なので、「どれくらいの速さで送っているか」を聞くのはやめて、
> 「**何を**送っているか」を聞くことにします。
>
> 今回のプロトコルは、ペイロードの中にフラグバイトを1つ持っています。
> TCPの真似です。意味を持つビットが5つ — SYN、ACK、FIN、などなど。
> 本物のクライアントは、意味の通る組み合わせを立てます。

[攻撃は走らせたまま、最後の diff を見せる。]

```bash
./stage.sh show 3
```

> 15行です。そして下の方の赤い行を見てください。
> **消す**のはこのステップだけです。
> 関数の末尾にあった、最初からずっと全部通していた `return XDP_PASS` —
> あれを、これが置き換えます。

```c
  __u8 *payload = (void *)(udph + 1);
  if ((void *)(payload + 4) > data_end) {
    inc_stat(3);
    return XDP_DROP;
  }

  __u8 flag = payload[3];
  if (flag != 0 && (flag & ~FLAG_VALID_MASK) == 0) {
    inc_stat(1);
    return XDP_PASS;
  }

  inc_stat(3);
  return XDP_DROP;
```

> まず境界チェック。verifier はまだ見ています。
> そもそもフラグバイトが入っていない? それは壊れたパケットなので落とす。
>
> そしてチェック本体。フラグバイトを取ってきて、質問は1つだけ。
> **既知のビットが少なくとも1つ立っていて、未知のビットが1つも立っていないか。**
> 以上です。AND 1回と、比較1回。
>
> 攻撃者が送ってきているのは 0xff。全ビット1です。
> つまり、このプロトコルで何の意味も持たないビットが立っている。だから不正。
>
> 状態なし。メモリなし。履歴なし。
> **誰が送ってきたかも、どれくらいの速さかも、一切気にしません。**

[攻撃は走らせたまま切り替える。guard が戻ってきた瞬間に
全員の目の前で数字が変わる。]

```bash
./stage.sh run 3
```

[攻撃を止めていた場合は、もう一度実行:
`attacker -target 10.10.0.2:9999 -mode evasive`]

> total は250のまま。dropped-rate は相変わらずゼロ —
> レート制限は**いまも突破されたまま**です。そこは何も直していません。
> そして dropped-protocol が250。passed はゼロ。

[静かになった victim ペインを指す。]

> サーバーは、自分が攻撃されていることを知りません。
> あのパケットを1つも見ていないので。
>
> そしてここが一番大事なところです。
> **あのパケットのために、何一つ確保していません。**
> sk_buff もなし、スタックを上がっていくこともなし、プロセスを起こすこともなし。
> パケットがまだ回線上のバイト列でしかない段階で、カーネルの中で決着している。
> だからユーザー空間側の処理は、そもそも一度も発生していません。

## 6. 締め（0:40）

[走らせたままの evasive に重ねて legit を実行する。]

```bash
attacker -target 10.10.0.2:9999 -mode legit
```

> 最後に一つ。本物のユーザーと、攻撃を、同時に流します。
> 毎秒6パケットが通っていて、毎秒250が落とされている。
> 本物のユーザーは、何も気づいていません。
>
> **ちゃんと機能している防御というのは、こういう見た目です。**
> 「なんとか耐えました」ではなく、「誰も気づかなかった」。
>
> 層が2枚、それぞれ別の質問をしています。「どれくらい」と、「何を」。
> 片方をすり抜けた攻撃者は、まだもう片方の前に立っています。
> これが多層防御です。
>
> それと、正直に言っておきます。**これは万能薬ではありません。**
> **正しいフラグバイト**を、ゆっくり、50個のポートから送ってくる攻撃者は —
> レート制限にも引っかからず、プロトコルチェックも通るので — いまも通ります。
> そうなったら、この2枚の上にもう1枚必要になる。
> 単独で勝てるチェックはありません。
> 層を1枚足すたびに、攻撃のコストが上がっていくだけです。
> そして、それがこの仕事の全部です。

## 想定質問と回答

**なぜその場で書かずにブランチを切り替えるのか?**
25行の eBPF 関数で打ち間違えると、10分の枠の半分が消えるからです。
diff に出ているのはその場で書いていたのと同じコードで、
コンパイルと verifier は目の前で走っています。

**なぜ iptables ではないのか?**
iptables はカーネルが sk_buff を確保した**後**に動きます。XDP はその**前**。
フラッディング下では、その差が勝負を分けます。

**verifier をもう一度説明して**
カーネル内の静的解析器です。プログラムが必ず終了すること、
メモリ範囲を出ないことを証明できて初めてロードします。
実行時のクラッシュではなく、ロード時の拒否です。

**攻撃者が正しいフラグを送ってきたら?**
通ります。そうなればレート制限＋アプリケーション層の防御が必要になります。
銀の弾丸ではなく、多層で戦うという話です。

**`inc_stat` は何をしているのか?**
total、passed、dropped-rate、dropped-protocol のカウンタをそれぞれ1つずつ
増やしています。ダッシュボードが読んでいるのがこれです。
CPUごとに持っているので、ホットパスでロックを取らずに増やせます。
読むときにユーザー空間側でCPUごとの値を合計します。

**レートのカウンタは競合しないのか?**
します。あのハッシュマップは全CPU共有で、インクリメントはアトミックではないので、
実際に並列に来ると少し数え漏らします。
レート制限の用途では問題ありません（ブロックがほんの少し遅れるだけ）。
厳密にやるなら per-CPU マップかロックが要ります。

**Goプログラムが死んだら?**
カーネル側はフィルタし続けます。既存のブロックはそのまま残り
（TTLで消す人がいなくなるだけ）、新しいレート超過も落ち続けます。
執行はユーザー空間に依存していません。

**これは実用のもの? おもちゃ?**
仕組みは実用です。Cloudflare や Meta が、まさにこの層で
XDPベースのDDoS対策を動かしています。
おもちゃなのは、今回でっち上げたフラグのプロトコルの部分だけです。

**なぜ UDP なのか?**
コネクションレスなので、ハンドシェイクなしで50個の送信元ポートから
簡単に送れるからです。
ペイロードのフラグバイトは、TCPの本物のフラグの代役です。

**IPヘッダのパースはどうなっているのか?**
（時間の都合で省略。あとで聞いてください。）`ihl` がヘッダ長を持っていて、
**単位が4バイト**です。20バイトだと決めつけると、長いヘッダを送られた瞬間に
全然違うバイトを解析し始めることになります。
