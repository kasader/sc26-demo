パスするのはこの2行のおかげ。画面はまだ何も意味していない状態にしておく —

**その場で書き損じたら:** 各ステップには、そのステップまで書き終わって

## 2. XDP と eBPF（3分）

> その答えが XDP です。ここで動くフックです。

[経路の一番手前、sk_buff より前を指す。]

> カーネルがまだ何も確保していない段階です。
> パケットは回線から届いたばかりで、メモリ上のただのバイト列でしかない。
> 私のコードはそのバイト列を見て、二つのうちどちらかを答えます。
> PASS — 通常のネットワークスタックにそのまま流す。
> あるいは DROP — この場で解放する。
>
> ここでの DROP は、ほぼコストゼロです。メモリ確保なし、解析なし、
> プロセスを起こすこともなし。
> しかも送信元には何も返りません。エラーすら返らない。
> つまり攻撃者は、何が起きたのか一切分からない。
>
> ここで当然の問題が出てきます。それはカーネルの中の話でしょう、と。
> どうやって自分のコードをカーネルに入れるのか。
> 昔はカーネルモジュールを書くしかなくて、書き間違えたらマシンごとパニックでした。
>
> そこで eBPF を使います。C言語で書いて、専用のバイトコードにコンパイルして —
> 普通の実行ファイルではありません — そのバイトコードを、
> 動いているカーネルに渡します。再起動なし、モジュールなし、クラッシュなし。
>
> そして「クラッシュしない」理由が、この技術の一番面白いところです。
> カーネルは、私の命令を1個も実行する前に、verifier（検証器）というものを走らせます。
> verifier は証明エンジンです。私のコードについて2つのことを証明しないといけない。
> **必ず終わること** — 無限ループがないこと。そして
> **許可された範囲の外のメモリを絶対に読まないこと**。
>
> 証明できなければ、私のプログラムはロードされません。
> あとで落ちるのではなく、そもそも受け付けてもらえない。
>
> なので、このあと一見不要に見えるチェックをいくつもお見せしますが、
> あれが何なのかを分かっていてほしい。
> あれは「念のため」ではありません。**あれが証明で、カーネルが採点している**んです。

[2つのネットワーク名前空間を指す。]

> 最後にもう一つ。これはコンピュータ2台とネットワークケーブル1本です。
> ただし3つともソフトウェアで、このコンテナ1個の中にあります。
> 左が攻撃側、右が被害側で、私のフィルタは被害側のケーブルの端に付いています。
> 実際のネットワークには一切触れません。

[2つのキャストを指す。]

> カーネルが渡してくるコンテキストの中に、パケットは入っていません。

> この下は全部、その範囲をバイト列として扱う作業です。

> お行儀の問題ではなく、**本当にロードされません**。

[iphdr のチェック、続けて ihl の行を指す。]

> IPも同じです。長さがあることを証明して、それからプロトコル番号を見る。
> UDPじゃない? PASS。
>
> ただ、ここは1つ見ておいてほしい。実際に世に出ているバグなので。
> IPヘッダは固定長ではありません。
> この `ihl` というフィールドが長さを持っていて、**単位が4バイト**です。
> 普通は合計20バイトですが、もっと長いこともある。
> もし20だと決めつけると、長いヘッダのパケットを送られた瞬間に、

> UDPヘッダの分の長さも証明する。これでポートが見られます。
>
> このブロック全体で気づいてほしいのは、
> 「自分に関係ないもの」はここまでで全部そのまま素通りしている、ということです。
> このフィルタは、マシンの他の部分からは見えていません。

## 6. レイヤ1: ブロックリスト（2分） ← ここからタイピング開始

仮置き2行の上。§9 までに書くものはすべて、`inc_stat(0);` とこの仮置き2行の

**入力するコード — その1（身元を作る）:**

  struct address_key src = {

**入力するコード — その2（参照）。すぐ下に続けて:**

  if (bpf_map_lookup_elem(&blocklist, &src)) {

## 9. レイヤ3（3分）

> なので、「どれくらいの速さで送っているか」を聞くのはやめて、
> 「**何を**送っているか」を聞くことにします。
>
> 今回のプロトコルは、ペイロードの中にフラグバイトを1つ持っています。
> TCPの真似です。意味を持つビットが5つ — SYN、ACK、FIN、などなど。
> 本物のクライアントは、意味の通る組み合わせを立てます。SYN とか、DATA + ACK とか。

**書く場所:** レート制限の閉じ `}` のすぐ下 — そしてここが唯一、先に
**消す**場所。ずっと関数の末尾に置いてあった仮置き（`// DEMO STEP` の
コメントと `inc_stat(1); return XDP_PASS;`）を消して、その位置にこのブロックを
書く。これで関数が終わる。消し忘れると、フラグチェックに届く前に全部
パスしてしまう。

**入力するコード — その1（境界チェック）:**

```c
  __u8 *payload = (void *)(udph + 1);
  if ((void *)(payload + 4) > data_end) {
    inc_stat(3);
    return XDP_DROP;
  }
```

> まず境界チェック。verifier はまだ見ています。
> そもそもフラグバイトが入っていない? それは壊れたパケットなので落とす。

**入力するコード — その2（チェック本体）:**

```c
  __u8 flag = payload[3];
  if (flag != 0 && (flag & ~FLAG_VALID_MASK) == 0) {
    inc_stat(1);
    return XDP_PASS;
  }

  inc_stat(3);
  return XDP_DROP;
```

> そしてこれが本体です。フラグバイトを取ってきて、質問は1つだけ。
> **既知のビットが少なくとも1つ立っていて、未知のビットが1つも立っていないか。**
>
> 以上です。チェックはこれで全部。AND 1回と、比較1回。
>
> 攻撃者が送ってきているのは 0xff。全ビット1です。
> つまり、このプロトコルで何の意味も持たないビットが立っている。だから不正。
>
> 状態なし。メモリなし。履歴なし。
> **誰が送ってきたかも、どれくらいの速さかも、一切気にしません。**

[guard をリロードする — §7 と同じコマンド。
攻撃は走らせたままにしておくと、戻ってきた瞬間に全員の目の前で数字が変わる。]

```bash
cd /src/sec-camp/guard && go generate ./... && go build -o /usr/local/bin/guard . \
  && ip netns exec vic /usr/local/bin/guard -rate 30 -block-ttl 15s \

```

[攻撃を止めていた場合は、もう一度実行:]

```bash
attacker -target 10.10.0.2:9999 -mode evasive
```

> total は250のまま。dropped-rate は相変わらずゼロ —
> レート制限は**いまも突破されたまま**です。そこは何も直していません。
> そして dropped-protocol が250。passed はゼロ。

[静かになった victim ペインを指す。]

> サーバーは、自分が攻撃されていることを知りません。
> あのパケットを1つも見ていないので。
>
> これが今日の要点です。
> 分散した攻撃者は、誰もが最初に作る層を突破しました。
> それを、AND 1個が全部止めた。
> 賢いからではありません。**まったく別の質問をしているから**です。
> レート制限が聞いているのは「どれくらい」。こっちが聞いているのは「何を」。
> 片方をすり抜けた攻撃者は、まだもう片方の前に立っています。
>
> これが多層防御です。しかもこれ全部が、カーネルの中で、
> パケットがバイト列でしかない段階で起きています。

## 10. 締め（1分）

[片方のペインで legit、もう片方で evasive を走らせる。]

> 最後に一つ。本物のユーザーと、攻撃を、同時に流します。
>
> 毎秒6パケットが通っていて、毎秒250が落とされている。
> 本物のユーザーは、何も気づいていません。
>
> **ちゃんと機能している防御というのは、こういう見た目です。**
> 「なんとか耐えました」ではなく、「誰も気づかなかった」。
>
> それと、正直に言っておきます。
> もし攻撃者が**正しいフラグバイト**を送り始めたら、この層は通してしまいます。
> そうなったらまたレート制限と、その上の層が必要になる。
> 単独で勝てるチェックはありません。
> 層を1枚足すたびに、攻撃のコストが上がっていくだけです。
> そして、それがこの仕事の全部です。

## 想定質問と回答

**なぜ iptables ではないのか?**
iptables はカーネルが sk_buff を確保した**後**に動きます。XDP はその**前**。
フラッディング下では、その差が勝負を分けます。

**verifier をもう一度説明して**
カーネル内の静的解析器です。プログラムが必ず終了すること、
メモリ範囲を出ないことを証明できて初めてロードします。
実行時のクラッシュではなく、ロード時の拒否です。

**攻撃者が正しいフラグを送ってきたら?**
通ります。そうなればレート制限＋アプリケーション層の防御が必要になります。
銀の弾丸ではなく、多層で戦うという話です。

**なぜ統計をCPUごとに持つのか?**
ホットパスでロックを取らずにインクリメントするためです。
読むときにユーザー空間側でCPUごとの値を合計します。

**レートのカウンタは競合しないのか?**
します。あのハッシュマップは全CPU共有で、インクリメントはアトミックではないので、
実際に並列に来ると少し数え漏らします。
レート制限の用途では問題ありません（ブロックがほんの少し遅れるだけ）。
厳密にやるなら per-CPU マップかロックが要ります。

**Goプログラムが死んだら?**
カーネル側はフィルタし続けます。既存のブロックはそのまま残り
（TTLで消す人がいなくなるだけ）、新しいレート超過も落ち続けます。
執行はユーザー空間に依存していません。

**これは実用のもの? おもちゃ?**
仕組みは実用です。Cloudflare や Meta が、まさにこの層で
XDPベースのDDoS対策を動かしています。
おもちゃなのは、今回でっち上げたフラグのプロトコルの部分だけです。

**なぜ UDP なのか?**
コネクションレスなので、ハンドシェイクなしで50個の送信元ポートから
簡単に送れるからです。
ペイロードのフラグバイトは、TCPの本物のフラグの代役です。

## 数字の早見表

| モード | 送信元 × pps | 合計 | 見えるはずのもの |
|---|---|---|---|
| legit | 3 × 2 | 6 | passed ≈ 6 |
| flood | 2 × 150 | 300 | dropped-rate 大、2件ブロック、のこぎり波 |
| garbage | 2 × 10 | 20 | dropped-protocol ≈ 20、ブロックなし |
| evasive | 50 × 5 | 250 | dropped-protocol ≈ 250、dropped-rate 0、ブロックなし |

しきい値は送信元あたり 30 pps。ブロックのTTLは15秒。

予備のデモが要るとき: `-mode legit -workers 1 -pps 60` —
**完全に正しいパケットなのにブロックされる**。レイヤ2は中身を見ていないので。
`garbage` のちょうど裏返しで、2つの層が別の質問をしていることを示せます。
